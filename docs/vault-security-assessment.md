# Personal Vault — Phase 1 security assessment

Review date: October 28, 2026. Status: **NOT APPROVED FOR SENSITIVE DATA**. This is an implementation review and architecture recommendation, not an independent penetration test or security certification. Phase 2 requires the owner's explicit approval of the selected design and cost before work starts.

## What this release does

Every existing Family profile has Overview, Wishlist, Important Dates and Vault tabs. Vault is a non-interactive layout with travel/identification, insurance and other-record categories. It prominently says “Secure storage not yet enabled.” There are no vault forms, uploads, keys, stored records, unlock sessions, reveal/copy controls, storage endpoints, migrations, provider connections or vault-reading tools. Disabled controls do not claim to provide protection. Existing profiles are reused, not seeded or duplicated.

Ordinary record reads and deletes now use an explicit allowed-kind list, excluding any future/foreign vault record. Ordinary writes reject unsupported kinds and reserved structured vault/secret fields. Reserved nested properties are omitted from legacy ordinary record responses. Both the HTTP app API and the MCP connector use these server-side boundaries. Tests insert synthetic foreign records into an isolated in-memory database to verify they are not returned, edited or deleted. No synthetic vault rows are inserted into production.

This is structural isolation, not data-loss prevention. A person could still paste an identifier into an existing ordinary free-text note, recipe or project; there is no reliable universal detector for arbitrary prose. The Vault tab offers no entry path and explicitly warns against putting secrets into ordinary notes or ChatGPT. Those existing features are not a vault. No real identifiers, documents or other sensitive family details were read or copied during this review.

## Current architecture and gaps

| Area | Observed implementation | Required before storage |
| --- | --- | --- |
| Hosting/identity | Private ChatGPT Sites app, Vinext/Cloudflare Worker. Protected pages and HTTP/MCP handlers require Sites-supplied user ID/email. Site access currently lists only its owner. | Verify adult identities separately. Sites membership is not vault authorization; owner/editor status and an editable profile's `role: parent` must never grant vault access automatically. Do not trust identity headers on an exposed alternative Worker origin. |
| Ordinary database | D1 generic JSON records and imported recipes, one shared household database; current profile and gift rules suit ordinary data. | Separate vault service/database and object bucket, not new secret fields inside `family`/`settings`/`notes`. No Homebase/MCP runtime credential with decrypt permission. Explicit per-person compartment ACLs on every operation. |
| Storage encryption | D1 and R2 platform documentation describes provider-managed encryption at rest and TLS. The app has no vault field/document encryption or key-manager integration. | Provider encryption alone does not protect against an authorized app, compromised Worker or database operator. Use reviewed end-to-end vault software, or authenticated envelope encryption with an external KMS and a separately authorized vault service. |
| Unlock | Homebase receives identity but has no verified recent-authentication claim, vault session or passkey challenge. | Fresh provider unlock or server-validated WebAuthn/user verification; short-lived session tied to adult account/device and compartment. Test challenge expiry, replay, revocation and no account/profile spoofing. |
| Connector | MCP reads the ordinary household model and can write supported ordinary records. | Keep vault schema, ciphertext, keys, document references and secrets out of these tools, searches, caches and recommendations. No vault-reading tool. Only an explicit, separately approved metadata projection may publish reminders later. |
| Browser | Shared frontend origin with ordinary household features. No dedicated vault CSP/session/isolation exists. | Prefer a separate provider origin and no secret display in Homebase JavaScript. If a custom vault is approved, isolate origin and session, remove third-party scripts, enforce a restrictive CSP, secure cookies, CSRF checks, rate limits and no caching/service-worker persistence of secrets. Masking alone does not protect data already sent to the browser. |
| Audit/logs | Generic records have last-update time/actor and version; no vault-specific append-only access audit exists. No vault request path exists. | Record actor, opaque object ID, action, result and timestamp without titles, field values or documents. Redact error/tracing bodies and URLs, verify platform log behavior with canaries, protect audit retention from ordinary edits. |
| Backup/recovery | D1 platform supports recovery facilities, but Sites tenant recovery access/retention and an end-to-end restore of DB+R2+keys have not been verified. | A documented, tested encrypted export/restore and account-loss process. Provider backup is not proof of recoverability. Include documents, key versions, ACLs and deletion/retention behavior; test on an isolated destination before real data. |

## Recommended direction

Prefer an established managed personal vault over custom cryptographic storage. For the complete stated scope, first evaluate **Bitwarden Teams with two adult accounts**, because Families lacks the requested event logs. Families is a lower-cost alternative only if the owner explicitly accepts that audit gap. 1Password is a viable comparison, subject to confirming equivalent auditing and recovery requirements. None of these recommendations is authorization to buy or connect anything.

Use one organization/system and five compartments, with an independently verified adult allowlist. Keep secrets and documents in the provider's own apps/origin, protected by its own unlock; Homebase can eventually offer a simple “Open secure vault” navigation and an explicitly approved, minimal expiration-reminder projection. Never store unlock credentials or a broad unlocked vault session in the Homebase Worker, browser bundle, ChatGPT tools, or public repository. No default shared vault that children inherit.

This recommended workflow deliberately opens the established vault interface rather than pretending it can be safely embedded in Homebase. Bitwarden's Public API manages organization administration, not vault item contents; the item-management HTTP interface requires a locally running CLI service. Deploying an always-unlocked bridge would materially expand risk and is not recommended. See [Public API](https://bitwarden.com/help/public-api/) and [CLI](https://bitwarden.com/help/cli/). Device unlock and re-lock behavior must be validated on the chosen provider's iPhone/tablet clients; a browser Face ID icon is not verification.

If viewing/editing secrets entirely inside Homebase is non-negotiable, pause for a second design review of an isolated vault service/origin, explicit WebAuthn step-up, per-record AES-GCM envelope encryption using maintained libraries, external KMS-wrapped data keys, authenticated compartment binding, and separated storage/credentials. Do not implement custom crypto algorithms or use an environment variable beside the database as the sole security improvement. No such service is implemented in Phase 1.

## Phase 2 approval and release gates

1. Owner explicitly approves the architecture, provider/plan, cost, recovery tradeoffs and adult identities. Merely approving the Phase 1 interface does not approve Phase 2 or a relaxed audit requirement.
2. Enroll the two adult accounts with MFA/passkeys and independent verification. Bind stable identities, not names or profile role labels, to each compartment. Default deny for children, other viewers, connector identities and revoked sessions.
3. Complete a synthetic-only proof of concept. Verify authorization for list/read/reveal/copy/create/update/delete/attachments and every direct endpoint; test guessed IDs, cross-person access, stale sessions, CSRF, replay, malformed data and rate limits. Require verified fresh unlock, default masking, explicit reveal/copy, short auto-relock and clearing sensitive UI state on lock/logout.
4. Confirm encryption/key ownership and rotation, exact document storage limits, log redaction and audit coverage. No persistent browser cache, analytics payload, query-string value, plaintext export, public bucket or raw document link. Document that screenshots, clipboard history, compromised devices and already copied data cannot be revoked by masking or logout.
5. Recovery drill: two adults confirm a trusted recovery arrangement; create an encrypted portable backup plus a complete document backup, keep recovery material separately offline, restore to an isolated test account, verify all records/files/permissions, and test loss of one adult account/device. Review the provider's export coverage: never assume record exports include every attachment. [Encrypted export guidance](https://bitwarden.com/help/encrypted-export/).
6. If a custom service is selected, restore ciphertext, documents, ACLs and required KMS key versions together; test old backups after rotation, key loss/deletion, and revocation. Set backup retention and deletion policy, protect separate encrypted backups and audit storage, and obtain an independent security review before production enablement.
7. Only after documented passing results and explicit release approval enable sensitive data entry. SSNs, passwords, recovery codes and other especially sensitive credentials remain outside Homebase Vault scope. No ChatGPT vault-reading tools are added.

**Phase 2 has not started. No real sensitive data should be entered yet.**
